# 4장 · 환불이 두 번 나갔어요

환불 서버가 느려서 응답이 안 올 때, 에이전트가 같은 환불을 다시 보내면 어떻게 되는지 세어 보는 장난감 실험이에요. 주문 10건에 장애 3개를 심고, 방어 방식 네 가지(변형 A~D)를 비교합니다. 파이썬 표준 라이브러리만 쓰고 난수가 없어서 몇 번을 돌려도 같은 값이 나와요.

## 실행

```bash
python3 double_refund.py        # 변형 A~D의 (환불 횟수, 지급 합계, 정답보다 더 나간 금액) 출력
python3 experiments.py          # results/ch04.json 생성
python3 -m pytest -q test_double_refund.py
```

## 변형

- A: 방어 없음. 응답이 없으면 그냥 다시 보내요.
- B: 다시 보내기 전에 서버에 "이미 환불됐나요?" 하고 상태를 먼저 물어요.
- C: 주문마다 같은 번호표(멱등성 키, Idempotency-Key)를 달고, 서버가 처음 본 번호표만 처리해요.
- D: 번호표는 다는데 보낼 때마다 새로 만들어요. C와 비슷해 보이는 잘못된 사용이에요.

## 검증하는 숫자

정답은 주문 10건의 환불 금액 합계 330이에요.

| 변형 | 환불 실행 횟수 | 지급 합계 | 정답보다 더 나간 금액 | 심은 장애 3개 중 막은 수 |
|---|---|---|---|---|
| A | 13 | 420 | +90 | 0 |
| B | 11 | 355 | +25 | 2 |
| C | 10 | 330 | 0 | 3 |
| D | 13 | 420 | +90 | 0 |

- 심은 장애: 3번·7번 주문은 서버가 환불을 끝낸 뒤 응답이 늦고, 5번 주문은 고객이 같은 메시지를 두 번 보내요.
- 더 나간 90은 3번 주문 50, 7번 주문 15, 5번 주문 25를 더한 값이에요.

## 경계

요청이 차례로 오는 실험이에요. 같은 키 요청이 동시에 들어오는 경우, 키가 지워진 뒤의 재시도, 같은 키에 다른 내용을 보내는 경우는 재지 않았어요. 가짜 모델이 아니라 실제 모델이 느린 응답 앞에서 어떻게 행동하는지도 이 코드로는 알 수 없어요. 실제 서비스가 멱등성 키를 지원하는지는 그 서비스의 공식 문서로 확인하세요.
