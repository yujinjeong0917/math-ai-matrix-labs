# 11장 · 틀린 환불이 나갔을 때 원인을 어떻게 찾고 어떻게 바로잡나요?

환불 처리 일곱 단계(접수, 분류, 조회, 판단, 실행, 안내, 기록)에서 장애 6가지를 하나씩 심고, 요청 번호가 붙은 기록이 있을 때와 없을 때를 비교한다. 또 4장 변형 C(같은 키로 환불을 한 번만 내는 방식)를 같은 키의 요청 둘이 서버 걸음 세 개(확인, 실행, 저장)를 섞어 실행하는 20가지 순서 전부에 돌려, 4장이 재지 못한 동시 요청을 센다. 표준 라이브러리만 쓰고 난수는 없다.

## 실행

```bash
python3 trace_recovery.py        # 결과를 JSON으로 출력
python3 -m unittest -v           # 테스트 7개
```

## 기대 출력(핵심)

| 항목 | 값 |
|---|---|
| 원인 찾기 확인 단계, 기록 없음(장애 6가지) | 3, 2, 5, 4, 5, 1 (합 20) |
| 원인 찾기 확인 단계, 요청 번호 있는 기록 | 모두 1 (합 6) |
| 복구, 요청 번호 있음 | 자동 재시도 2, 보상 입금 1, 사람 인계 3 |
| 복구, 요청 번호 없음 | 자동 재시도 0, 보상 입금 0, 사람 인계 6 |
| 보상 대상으로 의심되는 정산표 행 | 번호 있음 1행, 없음 4행(금액 30이 4행) |
| 동시 요청 20가지 순서, 4장 방식(확인 후 저장) | 이중 지급 18가지, 최대 지급 2회 |
| 동시 요청 20가지 순서, 확인과 자리 잡기를 한 번에 | 이중 지급 0가지, 최대 지급 1회 |

## 이 실습이 확인하지 못하는 것

확인 단계 수("증상이 보인 단계에서 거꾸로 한 곳씩 연다")와 복구 경로 규칙은 이 장난감이 정한 가정이다. 실제 결제 서비스가 이미 나간 환불을 취소하거나 정정하는 방식은 서비스마다 다르며 재지 않았다. 동시 실행은 실제 스레드가 아니라 걸음을 섞은 순서를 나열한 것이고, 4장 코드의 세 동작을 따로 일어나는 세 걸음으로 본 가정이 들어 있다. 실제 서버가 키를 어떻게 저장하는지는 그 서비스의 공식 문서로 확인해야 한다. 가짜 모델이라 실제 모델이 오류를 만났을 때 하는 행동은 재지 않는다.
